本界面将记录特别重要的，且多模块联合更新的页面。在此记录版本号的内容将不会在各自的专属更新日志页面中重复书写。

重要公告与说明
  1. 校检器更名与功能合并：
    原「校检器」正式更名为「签名发布器」（英文全称 Shiori Signer 不变，后续简称「签发器」），并与原「补丁器」（Shiori Package / Shiori Patch）完成功能合并；原补丁器（V1.0.1）已并入签发器并下线。
  2. C++ 版启动器无限期搁置:
    出于技术栈避嫌（Kirikiri 底层使用 C++），已被宣布立项的C++ 版启动器将无限期搁置且不会上线。虽然其当前功能已基本达到 V1.2.7 版启动器的水平，但后续不再维护。
  3. 名词区分：签发器 / 补丁器 / 专属签发器:
    「签发器」指签名发布器（ShioriSigner.exe），在开发机上使用；「补丁器」（ShioriPatch.exe）由签发器产出，是发给玩家的单文件增量安装程序；「专属签发器」（ShioriVerify.exe）随游戏分发，供玩家双击自校检。三者用途与分发对象各不相同.
功能新增部分：

引擎核心
  • 新增 .ks 格式支持
  • 旧版本的正则 DSL 扩展性较差，本次新增 .ks 文件支持，可在此类文件中编写宏。具体用法见 KSmacro.html；若不使用 .ks，可忽略本条并继续用 JS 开发。

    • 说明：仅借用 Kirikiri 的 KAGScript 文件格式，语法虽相似但「与 Kirikiri 的 ks 不同」，不能将 Kirikiri 的 ks 直接放入本引擎使用；但可使用 ks 的语法高亮。

  • 迁移说明：旧版剧本只需修改引用即可无痛迁移到新引擎，无需改动剧本正文，旧剧本内容与本次引擎更新完全兼容。

    • 宏示例：
    [macro name=BGM渐升]
    [BGM play storage=%storage|bgm1.ogg vol=%vol|20%->100% time=%time|1000]
    [endmacro]
    该宏作用：令 bgm1.ogg 以 1 秒速度从 20% 音量渐变到 100% 后，以 100% 音量持续播放。
    剧本中调用宏：command: "@BGM渐升"。整体写法虽与 Kirikiri 的 ks 相似，但语法不同。


变量与运算符系统
  • 剧本内新增变量语句区：把一整段变量操作放进 command 字段、用 $ 引导，支持赋值与复合赋值（= += -= *= /=）、自增自减（++ --）、占位符 ~，以及 ?条件 | 真分支 | 假分支 条件分支；条件表达式限定白名单，写错会在编译期与运行期各记一条诊断，不再静默失效。

    • 运算符全表、条件白名单，以及「vars 动作」与「$ 语句区」两个写变量入口的差异对照，见教学页 变量与运算符。

    剧本中两种写法的区别：旧写法是把变量操作写成 action 里的一个 vars 动作（{ type: "vars", op: "setSF", name: ..., value: ... }），能力有限、不受编译期校验，且会停在该行等点击；新写法是把整段操作放进 command 字段（command: "$sf.clear = 1"），编译期与运行期各校验一遍、写完自动推进，并支持复合赋值、自增自减与 ?条件 | 真 | 假 分支。两者写入同一套变量空间，差异对照见 变量与运算符 2。系统变量另有两道保护（见 变量与运算符 7）：tf.allclear 是宿主调试开关（「开启全部鉴赏」），剧本与插件一律写不了；sf.clear 是通关标识，只接受写 1，0 只是默认状态、置 1 后剧本无法回退，唯一清零通道是设置里的「清除存档」（resetSystem）。

    签名发布器（签发器）部分
  • 签名格式升级（SHA256/PSS/RSA）
    1. 现行签名文件头为「-- SIGNATURE - SHA256/PSS/RSA --」，总清单为「-- SIGNATURE - SHA256/PSS/RSA - MANIFEST --」。
    2. 签名算法为 RSA-PSS + SHA256，每条签名载荷为「相对路径 + 换行 + 哈希」，防止 A 文件的签名被挪到 B 文件上使用。
    3. 签名文件内分段记录 -- PATH -- / -- FILES -- / -- EXTERNAL -- / -- RSA -- / -- KEY ID --；KEY ID 为签发公钥指纹（SHA256(SPKI DER) 前 16 位十六进制）。
    4. 发行布局：每个受保护目标同级生成 <目标>.sig，内容根生成 release.sig 总清单，公钥随附 public_key.pem。
    5. 旧版签名（文件头「-- SIGNATURE - SHA256 --」/「-- SIGNATURE - SHA256 - MANIFEST --」：集中式目录 shiori engine\SHA256 + manifest.sig）仍可读取并比对哈希，但不含 RSA 段，不具备抗篡改能力（即无法防止非开发者重新为游戏生成完整配套签名）。
    6. 旧版发行包需用本版本重新生成签名后，整套签名才具备抗篡改能力。
    7. 开启「严格模式（缺少 RSA 签名即判失败）」时，不含 RSA 段的签名一律按失败计。
    8. 向前兼容：仍可校检旧版已生成的 SHA256 编码，也可生成旧版未加密文件的 SHA256 编码；同时可为未加密文件生成带 SHA256/PSS/RSA 签名的新版 SHA256 编码，且生成位置与之前完全一致。
  • 专用资源容器格式（.sgd）
    1. 容器魔数头为 8 字节 ASCII「SHIORIPK」（十六进制 53 48 49 4F 52 49 50 4B），位于文件开头（偏移 0~7），是识别 .sgd 容器的唯一特征；读取侧先校验魔数与版本号（当前版本 1），不匹配一律拒绝打开。
    2. 容器头为 64 字节定长明文区：魔数(0~7) / 版本 u32(8) / 标志 u32(12) / 头部密文长度 u32(16) / 条目数 u32(20) / 扇区对齐 u32(24) / 头部 IV(48~63)；多字节字段统一大端序（BE）。
    3. 标志位定义：1 = 头部加密、2 = 含授权文件、4 = 子包。
    4. 头部之后为密钥包裹区：Key ID 长度 u16 + Key ID 字符串（打包公钥 SPKI 的 SHA256 十六进制）+ 包裹长度 u32 + RSA-OAEP(SHA256) 包裹的数据密钥 DEK；Key ID 不符即拒绝解包。
    5. 头部区内容为「条目表 + RSA-PSS 签名 + 末尾 u32 签名长度」，由 HKDF(DEK, "shiori/hdr") 派生的头部密钥经 AES-256-CTR 加密；签名长度写在末尾，读取侧无需预知条目表长度即可反解。
    6. 数据区每条资源一条记录：名称长度 u16 + 逻辑名称 + 数据偏移 u64 + 密文长度 u64 + 明文长度 u64 + 12 字节 Nonce + 32 字节明文 SHA256 + 编解码器 u8 + 标志 u8。
    7. 编解码器：0 = 明文（读取即原文），1 = AES-256-CTR（以 nonce(12) || 计数器 u32 作为 AES-ECB 输入生成密钥流后异或），2 / 3 为预留。
    8. 读取时逐条用定长时间比较校验明文 SHA256，不一致即判定内容被篡改或密钥不匹配。
    9. 发布时按目录分包：cg、ui 目录为明文包，其余目录、assets 各子目录、站点根散文件（code.sgd）各自成包，默认统一走 AES-256-CTR 加密。
    10. 每个 .sgd 同级生成一份明文 .sig，容器本身纳入外层签名体系统一保护。

      11. 注意：请勿分发或发布你的密钥（尤其是私钥），也切勿遗失密钥，否则将无法找回，且无法对已发布的游戏进行补丁式更新。请务必在本地或私有云端多处保存好已发布游戏的密钥文件。

  • 加密与发布窗口
    1. 「加密与发布」窗口内置「① 密钥管理」与「② 加密打包发布」两页，顶部页签可随时来回切换。
    2. 主窗口入口为「加密与发布」「生成签名」「校验完整性」三个按钮。
    3. 密钥管理页提供：生成密钥对、显示 / 复制公钥与私钥、导出密钥为 txt、导入密钥 txt、清空密钥、应用到本次会话。
    4. 加密打包发布页提供：源目录、输出目录、打包选项（编译专属启动器 Shiori.exe / 部署原生内核 ShioriCore.dll / 打包后自校验读取 / 生成 .sig 校验文件）、开始加密打包发布。
    5. 发布产物为发布根下的内容目录（含 shiori engine、public_key.pem、release.sig 与各 .sig，以及随游戏分发的专属签发器 ShioriVerify.exe）与 developer_keys 密钥备份目录，以及 launcher_priv.pem、launcher_pub.pem。

      6. 注意：发布时需要启动器源码以编译专属启动器。

  • 密钥与打包同源
    1. GUI 中仅有密钥管理页一个密钥生成入口，RSA 位数严格按下拉框选择执行（2048 / 3072 / 4096），默认 3072。
    2. 打包密钥默认使用密钥管理页的会话密钥，生成与打包使用同一把密钥。
    3. 打包密钥可切换为「使用指定 PEM 文件」，该选择会被记住，不会被自动改回。
    4. 新增「另存为 PEM...」，将当前生效的打包密钥导出为 launcher_priv.pem 与 launcher_pub.pem。
  • Key ID 全程可见
    1. 密钥管理页生成、导入后立即显示当前密钥的 Key ID 与位数。
    2. 打包页常驻显示「本次打包密钥 Key ID」（含位数与来源），打包前即可确认所用密钥。
    3. 导出的密钥 txt 与 launcher_priv.pem 末尾均标注 Key ID，离线保管时也能一眼核对。
  • 校检自动匹配随包公钥
    1. 校检时若当前持有的密钥与签名记录不一致，自动改用发行包随附的 public_key.pem，并在日志中提示。
    2. 验签结果同时列出「签名记录 Key ID」与「当前公钥 Key ID」，密钥是否配对可一眼核对。
  • 命令行校检
    1. 新增 --verify：ShioriSigner.exe --verify --site <目录> [--pub <公钥.pem>]。
    2. 校检结束输出 VERIFY_EXITCODE（0 为通过，2 为存在失败），供脚本与自动化流程直接调用。
  • 专属签发器（ShioriVerify.exe，随游戏分发）
    1. 发布时在内容根额外产出一个独立校检程序，玩家双击即可校检本游戏，无需安装管理器。
    2. 以 C++ 编写、不依赖任何运行库，体积约 0.2 MB（同功能的 .NET 程序为 100 MB 级）。
    3. 与本次发布的那一款游戏绑定：公钥指纹、公钥本体、发布基线三重绑定，拷到别的游戏目录即被拒绝；校检只读内置公钥、不读同目录的 .pem，替换公钥也无法蒙混通过。
    4. 只读、不联网、不提权；除玩家主动「导出报告」外不写任何文件。
    5. 打开窗口后由玩家点「开始校检」再执行，过程逐条输出，便于观察大文件校检进度。
    6. 支持静默模式 /silent 并返回退出码（0 通过 / 2 存在失败 / 3 自身被篡改 / 4 非本游戏），供脚本与自动化流程调用。
    7. 签发器签发时的记录与当前内容不同时只给出中性说明（常见于已安装补丁或版本更新），不影响校检结论。
  • 发布补丁包（增量补丁，原Shiori Package整合部分）
    1. 「加密与发布」窗口新增「③ 发布补丁包」页：指定被改 / 新增的源目录或散文件，以及已发布的完整游戏内容根，即可产出单个补丁安装程序 ShioriPatch.exe。
    2. 自动识别目标状态并据此安装：完整的 .sgd 加密 / 明文 + 公私钥 256 / 明文 + 仅 256 / 明文（无 256）；开发者只需给出被改动的文件，程序自动归入对应 .sgd 包或对应目录。
    3. 加密目标走条目级增量：只就地改写受影响的 .sgd，未变动条目的密文逐字节不变，随后重出该包 .sig 与内容根 release.sig。
    4. 明文目标走文件级增量：只落地被改 / 新增文件并重算 shiori engine\SHA256\manifest.sig，保持原有明文布局，不新建 .sgd。
    5. 以完整文件集为基准：.sig / release.sig / manifest.sig 一律按补丁后的全量目标签发，而不是只覆盖被改动的文件。
    6. 同密钥硬校验：加密目标与带 RSA 的明文目标必须由开发者显式提供与该游戏公钥指纹一致的私钥 .pem，未提供或指纹不符即拒绝生成。
    7. 补丁自带前身版本核对：安装前比对当前游戏是否为本补丁对应的上一个版本，不符仅提示、不拒绝安装（「仍要安装」/「取消」）。
    8. 不重编译启动器：Shiori.exe 与 ShioriCore.dll 原样保留，补丁只写 .sgd / .sig / release.sig / manifest.sig。
    9. 补丁自身带完整性自检：启动即以尾部签名与内置公钥校验自身，并对内置增量载荷验签，防掉包与字节级篡改。
    10. 安装时同步释放专属签发器：与本次补丁匹配的 ShioriVerify.exe 内嵌在补丁内一并替换，因此只需分发一个补丁文件，不会出现「补丁更新了、签发器忘换」导致的长期误报。

    • 离线编译补丁包的nupkg依赖包从原来的8个扩充至18个

    • 管理器部分
    • 校检签名将兼容现有的签名格式。
    • 文件格式检测将支持专有容器 .sgd 检测。
    • 当游戏中填写了网址时，现在可通过管理器直接在外部浏览器打开游戏官网。

      • 请注意：这些链接均为开发者写在游戏中的网页链接，大概率为游戏官网或补丁网站，并非 Shiori 官方网页，Shiori 官方不对这些网页的安全性负责。

    • 更新月幕数据包（release：2026/10/9），条目数量变更：31546→31629

    优化内容

    引擎核心
    • 源代码优化：将原近万行代码的引擎核心运行时 engine.js 按模块拆分为十余个 JS 文件，并在 Shiori engine 文件夹内新建 ui / system / engine 等子文件夹，便于后续维护。
    • 新版立绘系统优化：新版立绘在拼接后不再被视为多张图片，而是被视为一张图片，快速点击移动时错位几率大幅降低。
      原 engine.js 处理：将 img.char-dress 与 img.char-face 各自作为一张图，使用两个 DOM 节点，导致快速点击渲染时会错位。
      现 engine_chars.js 处理：通过 computeCharDiffFaceRect 算出 face 落位矩形，用 drawImage 两级叠加后合成单张图并使用同一 DOM 节点；简言之，将 face 的像素按矩形「烧」进 dress 画布中。
    • 剧本减重：现在不再需要在剧本中引用近十个文件与通用 UI 设置，这些内容现由 page-chrome.js 统一管理，每个剧本文件减少六十余行重复代码。
    • 启动器读取策略：启动器现在会无条件读取 Shiori engine 文件夹内的 js / css / ks / json 文件。若需引擎按需按顺序读取文件，请到 engine_manifest.json 中设置即可。

      • 请注意不要重复放置相同或相似的代码在引擎文件夹中，以免发生不可控的错误。

    • CSS 优化：现在不再使用 CSS 的响应式设计来做响应式优化，删除大量 CSS 样式，改为与 C# 窗口同步大小的等比缩放，彻底解决边界问题，并限定窗口最小尺寸。
    • BGM 页面优化：下方的 UI 不会再因页面过小而遮挡 BGM 列表。
    • 画面大小优化：现在关闭画面后，下一次打开画面的窗口大小将继承上次关闭时的大小，不再回归默认状态。
    • CG 页面优化：现在 CG 页面加载时间大幅减少，且不会再出现卡顿、滚动时图片预览错位的情况（内部经暴力测试：将 29 张图片以 500 倍倍率输出并全部视为独立 DOM 加载，仅较靠后的内容加载稍慢；但即便商业作品也用不到这么多张 CG 图片）。
    • 音频播放优化：现在打开任意含 BGM 的页面后会自动播放 BGM，不再需要先点击一次页面才会播放。
    • 开发者窗口：F1 / F2 两个开发者专用窗口现在在 Release 中被屏蔽，转为 Debug 专属内容；为保护加密游戏文件代码，F12 也同步在 Release 中被屏蔽。
    管理器
    • 修复了无法检测到 8080 端口占用、且无法杀掉本引擎游戏进程的问题（现在不仅能检测 8080，还能检测电脑当前所有被占用的端口）。

      • PS：启动器源码是开源的，可在代码中将 8080 端口改为其他任意数字，以免默认端口冲突。

    • 优化了「只能杀掉当前打开的 Shiori 游戏」为「会杀掉被打开的其他 Shiori 游戏进程」（非 Shiori 引擎游戏可能无法杀掉进程，也不做越权管理），从而启动本次被点击启动的游戏。
    • 现在 UI 会自动换行，不再重叠或被遮挡。
    签名发布器（签发器）
    1. 窗口高度自适应
      1. 加密与发布窗口与主窗口不再限定固定高度，改为按内容自然撑开。
      2. 高度上限为屏幕可视区域，内容超出后由内容区滚动，不会超出屏幕。
      3. 切换页签时按当前页内容重新适配高度。
      4. 密钥框与执行日志区高度随内容增长，不再写死固定值。
    2. 发布前置说明
      1. 加密打包发布页顶部新增可折叠的「发布前置条件与注意事项」，列出前置源代码依赖、目录怎么摆、发布注意事项与推荐做法；默认收起，展开后窗口按内容自动适配高度。
